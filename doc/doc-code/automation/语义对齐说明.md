## 📋 结构图（两套语义并列）

### 原版 EvoFlow：automation 是一条「无人值守自动化流程」子系统

```text
evoflow/
├── automation/
│   └── output_paths.py         prompt-only 自动化产物的规范化输出路径
├── agents/
│   └── automation_runtime.py   无人值守运行辅助（trigger 标记 / 判定 / 场景预绑定）
├── app/gateway/
│   ├── automation_chat_session.py  把定时 run 挂到 EvoPanel 侧边栏会话
│   └── automation_runner.py        Gateway 后台调度器（tick 扫任务 → LangGraph runs.wait）
└── scheduler/                  ⚠️ 原版这里是「工具执行引擎」，与定时无关
    ├── engine.py               LocalToolScheduler：TaskPlan → op 分层执行
    ├── rules.py                tier0/tier1/tier2 分层规则
    ├── task_plan.py            <task_plan> JSON 解析成 TaskOp 列表
    ├── tool_executor.py        execute_op：真正调 read/search/write/run
    └── prefetch_stream.py      索引搜索 + 并行读文件预热上下文
```

### AgentFlow M5：automation 这个词被借去命名「定时任务」的数据层

```text
agentflow/
├── scheduler/                  ← M5 自造：定时触发器
│   ├── cron.py                 手写 5 字段 cron 匹配（normalize + matches_at）
│   └── loop.py                 AutomationScheduler daemon tick（扫库→命中→入队）
└── persistence/
    └── automation_repositories.py  automations（任务定义）+ automation_runs（执行历史）两表
```

> **一句话差异**：原版的 `automation/` 是「后台无人值守地跑一整个 agent，产出规范化交付物」的完整流程子系统；AgentFlow 的 `automation_repositories.py` 只是「cron 定时任务」这一概念的 SQLite 持久层——名字撞了，语义不对齐。

## 💡 设计思想：原版 automation 到底是什么

原版 automation 的核心是 **「无人值守（unattended）跑一次 agent」**：没有真人在会话里等结果，到点由后台把一段 prompt 喂给完整 LangGraph agent，跑完把产物写到固定目录。四个支柱：

1. **trigger 标记（`agents/automation_runtime.py`）**：三个常量 `automation_scheduler` / `proactive_engine` / `unattended_task_queue` 刻在 runtime context 里；`is_unattended_automation()` 据此判定本次运行是不是无人值守。判定为真后：预绑定场景（默认 `agent`）、跳过 `ScenarioNotActivated` 交互 gate、启用 AutomationRunGuard（限制工具轮数）。
2. **prompt-only 产物规范化路径（`automation/output_paths.py`）**：默认产物落在 `~/.evoflow/outputs/automations/{automation_id}/{YYYYMMDD}.md`，也支持 TOML `output_path` 模板。它还生成一段「【交付文件 · 必须遵守】」prompt 块，硬性要求 agent：把完整结果写进指定文件、结案用 `tasks` 工具 outputs 数组登记该文件、文件没写成功前**禁止**标 completed。
3. **gateway 自动化会话（`app/gateway/automation_chat_session.py`）**：把每次无人值守 run 映射成 EvoPanel 侧边栏一行会话——`fresh` 模式每次 run 一行、`sticky` 模式每个任务一行；标题格式 `定时·{任务名}·{mm-dd HH:MM}`；新行默认折叠（hidden），不打扰主聊天列表。
4. **gateway 后台运行器（`app/gateway/automation_runner.py`）**：在 Gateway 进程里跑 60s tick，扫任务定义目录（`~/.evoflow/tasks/automations`），命中后走 LangGraph `runs.wait` 直跑完整 agent。它明确支持三种执行路径：绑定已发布 workflow（走 app_runner）、prompt-only（默认直跑 LangGraph）、prompt+opt-in（Task Center 无人值守 plan→dispatch）。每条 run 前注入「自动化模式 · 必须遵守」外层规则——禁止调用任何「向用户提问 / 等待确认 / 等待输入」的工具。

**关键认知**：原版 automation 不是「定时触发器」本身，而是「**定时到了之后，怎么以无人值守方式跑完一次完整 agent 并产出交付物**」这一整套流程。定时 tick 在 `automation_runner.py` 里，但它只是这套流程的入口；真正的语义重心在「无人值守运行时 + 产物规范 + 会话可见性」。

## 📋 AgentFlow M5 是什么语义

AgentFlow M5 服务的是一个**更窄的用户需求**：用户自己规划一条「每天 9 点 / 每分钟 echo」的定时任务，到点把预设 prompt 丢给 agent 跑。它由三块组成：

1. **`scheduler/cron.py`**：手写 5 字段 cron 匹配（零第三方依赖，不引 croniter）。`normalize_schedule()` 把用户乱填的写法兜底成标准 cron（默认每天 09:00），`cron_matches_at()` 判断某时刻是否命中调度（支持 `*` `,` `-` `*/n`，DOW 按 JS 约定 0=周日）。
2. **`scheduler/loop.py`**：`AutomationScheduler` 是一个 daemon 线程，每 60s tick 一次：`repo.list_active()` 扫全部 active 任务 → `cron_matches_at` 命中 → 分钟级去重（同分钟只入队一次）→ once 型幂等校验 → `queue.put((task_id, prompt))`。**tick 线程只扫库 + 入队，绝不建 agent、不碰模型**；真正执行留给 REPL 主线程 drain 队列时。
3. **`persistence/automation_repositories.py`**：两张表——`automations`（任务定义：task_id/name/prompt/schedule/schedule_type/status/once_fired/last_run/run_count）+ `automation_runs`（执行历史：run_id/started_at/finished_at/status/output/error/duration_seconds）。delete 只删任务行，runs 历史保留。

**关键认知**：AgentFlow 的 "automation" = 「cron 定时任务」，是用户视角的一个**触发器 + 一条任务记录**。它没有原版那套「无人值守运行时标记 / 规范化产物目录 / 侧边栏会话」。

## 📊 差异本质对比表

| 维度 | 原版 EvoFlow automation（无人值守自动化流程） | AgentFlow M5 automation（定时任务） |
|---|---|---|
| **触发方式** | Gateway 后台 tick 扫任务定义目录 → LangGraph `runs.wait`；每次 run 在 runtime context 刻 `triggered_by=automation_scheduler/proactive_engine/unattended_task_queue` | daemon tick 扫 SQLite `automations` 表 → `cron_matches_at` 命中 → `queue.put((task_id, prompt))`；无 trigger 标记概念 |
| **运行形态** | 完整无人值守 agent run：pre-bind 场景（默认 `agent`）、跳过交互 gate、AutomationRunGuard 限轮数、外层规则禁止提问/确认类工具 | tick 线程**只投递不执行**；执行权在 REPL 主线程 drain 队列；无人值守判定、场景预绑定、轮数 guard 都没有 |
| **产物** | prompt-only 产物规范化写 `~/.evoflow/outputs/automations/{aid}/{YYYYMMDD}.md`；output_paths.py 强制「写文件 + tasks outputs 登记 + 禁止提前 completed」 | `automation_runs` 表记 run 元数据（status/output/error/duration）；**无规范化产物目录约定**，产物落哪由执行端自由决定 |
| **会话可见性** | automation_chat_session.py 把每次 run 挂成 EvoPanel 侧边栏一行（fresh/sticky），标题 `定时·{name}·{mm-dd HH:MM}`，新行默认折叠 | 无 sidebar 会话概念；靠 CLI `list` 看任务、查 `automation_runs` 表看历史 |
| **与 scheduler 关系** | 原版 `scheduler/` 是**工具执行引擎**（TaskPlan→op 分层执行），automation_runner 可直跑 LangGraph（不经 plan worker），也可 opt-in 走 Task Center | AgentFlow `scheduler/` **本身就是定时触发器**（cron+loop），automation_repositories 只是它的数据层；没有「工具执行引擎」这一层 |
| **任务定义存储** | TOML 目录 `~/.evoflow/tasks/automations`（+ SQLite 表），支持绑定已发布 workflow / 选择执行模式 | SQLite `automations` 表（task_id/name/prompt/schedule/...），纯 prompt 任务 |

## 🎯 后续对齐方向（M8.1，当前不改代码）

> 本节是**方向性建议**，不是本次交付的执行项。本次只写文档。

1. **新建 `agentflow/automation/` 包**：把原版 `automation/output_paths.py`（规范化产物路径 + 交付文件 prompt 块）移植过来，让无人值守 run 的产物有固定落点（如 `~/.agentflow/outputs/automations/{aid}/{YYYYMMDD}.md`）。
2. **补无人值守运行时标记**：参考 `automation_runtime.py`，在 AgentFlow 的 run context 里加 `triggered_by` 维度（automation_scheduler / manual / ...），让执行端能区分「这是定时触发、不该调交互类工具」。
3. **gateway 会话挂接**：M7 已有 `app/gateway/`，后续可在自动化 run 启动时 upsert 一条侧边栏会话（参考 `automation_chat_session.py` 的 fresh/sticky 模式），让定时 run 在 UI 里可追溯。
4. **scheduler 分层**：原版 `scheduler/engine.py` 那套「TaskPlan→分层执行引擎」是另一个话题，见 [`../scheduler/语义对齐说明.md`](../scheduler/语义对齐说明.md)。AgentFlow 当前 `scheduler/` 是定时触发器，未来要演化出执行引擎时应**另立模块**，不要和 cron/loop 混在同一个 `scheduler/` 包里。
5. **命名建议**：长期可考虑把 `automation_repositories.py` 的表语义从「定时任务」正名为「scheduled tasks」，把 `automation/` 这个名字留给真正的「无人值守自动化流程」子系统——避免原版那种「automation 一词两义」的混淆在仿写版重演。

## ❓ Q&A / 知识点

### 1. 为什么 AgentFlow M5 会和原版语义不一样？

**一句话**：M5 当时只取了原版的「定时触发侧」（tick 循环 + cron 匹配），没有移植「无人值守运行时侧」（trigger 标记 + 产物规范 + 会话挂接）。

M5 的目标是验收演示「每分钟 echo / 每天 9 点跑一个 prompt」，最小实现就是 cron 匹配 + tick 入队 + SQLite 存任务。原版那套 `output_paths.py` / `automation_runtime.py` / `automation_chat_session.py` 服务的是「生产级无人值守跑完整 agent 并出交付报告」，M5 阶段用不上，就没移植。审计差异 #2/#3 就是把这个「当时没移植」显式记录下来，避免后人以为 AgentFlow 的 automation 已经对齐原版。

### 2. AgentFlow 现在的 `automation_repositories.py` 和原版同名文件是什么关系？

**一句话**：表结构对齐，但语义承载不同。

两边都叫 `automation_repositories.py`、都有 automations / automation_runs 两表；但原版那套表背后挂着 gateway runner + chat session + output_paths 的完整流程，AgentFlow 这套表背后只挂着 cron tick + queue。名字撞了，是因为 M5 对齐了「持久层表结构」，没对齐「上层流程」。

### 3. 原版 automation_runner.py 那么大（60KB），AgentFlow loop.py 只有 7KB，差在哪？

**一句话**：原版 runner 是「真跑 agent」，AgentFlow loop 是「只入队不跑」。

原版 `automation_runner.py`（60KB）里做了：扫 TOML/SQLite 任务、并发信号量控制 LangGraph 并发、拼外层规则 prompt、调 `runs.wait` 跑完整 LangGraph、挂接 chat session、写 run 状态、处理失败重试。AgentFlow `loop.py`（7KB）只做了：扫 active 任务、cron 命中判断、分钟级去重、`queue.put`——它**故意不碰模型**，把执行留给 REPL 主线程。这是 M5「tick 线程绝不建 agent」的刻意设计，但也意味着它离原版 runner 的完整功能还很远。

## ⚠️ 风险点

1. **命名混淆是长期债务**：AgentFlow 现在 `automation_repositories.py` 里的 "automation" = 定时任务，而原版 `automation/` 包 = 无人值守流程。后续移植原版 `automation/` 包时，必须先想清楚命名归属，否则两个 automation 会撞车。
2. **不要把 cron/loop 当成原版 scheduler**：原版 `evoflow/scheduler/` 是工具执行引擎（见 scheduler 语义对齐说明），AgentFlow `agentflow/scheduler/` 是定时触发器。引用原版 scheduler 设计时不要直接套。
3. **本说明是方向性记录**：里面提到的 `output_paths.py` / `automation_runtime.py` 对齐项都是 M8.1 的事，当前 pytest 164 基线不动。
