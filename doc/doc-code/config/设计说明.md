# config 域 —— 配置怎么变成对象

## 1. 文件清单（对应真实代码）

| 文件 | 一句话职责 |
|---|---|
| `config/app_config.py` | **总入口**：读 config.yaml 文件 → AppConfig |
| `config/model_config.py` | 类型定义：ModelConfig + ChatModelConfig |
| `config/models_yaml.py` | **解析器**：models 段 dict → ModelConfig |
| `config/paths.py` | 路径定位：项目根 / data 目录 / 数据库路径 |

## 2. 设计说明（调用链）

```
paths.py（先定位: parents[5] = 项目根）
   │
app_config.load_config(path?)            ← ① 读文件（唯一"读取器"）
   │  路径优先级: 参数 > AGENTFLOW_CONFIG_PATH > config.yaml
   │  yaml.safe_load(f) → raw dict
   ├── raw["log_level"]                  ← ② 全局字段直接取
   ├── raw["paths"]["data_dir"]          ← ③ 数据目录
   └── raw["models"] ──► models_yaml.load_models_from_yaml(raw)
                                           │ ④ 解析 models 段
                                           ├─ chat.provider/base_url/model/temperature
                                           └─ api_key 走 _resolve_env 展开 ${ENV}
ModelConfig(chat=ChatModelConfig(...))    ← ⑤ 类型化完成，交给调用方
```

**关键设计**：
1. **读取与解析分离**：`app_config` 管文件来源，`models_yaml` 管类型转换——测试 models_yaml 只需传 dict，不用建文件
2. **密钥不落 yaml**：api_key 写 `${ENV}` 占位，`_resolve_env()` 运行时从环境/.env 取
3. **容错**：config.yaml 缺失不抛错，返回全默认（cli 再校验关键字段）

## 3. 你问过的问题总结（Q&A）

**Q1：models_yaml 是不是向外提供方法、获取 config 数据？**
A：是"向外提供方法"，但它是**解析器不是读取器**：
- 对外函数：`load_models_from_yaml(raw: dict | None) -> ModelConfig | None`
- 它**不读文件**，接收的是 yaml 解析后的 dict（`raw.get("models")`）
- 真正读文件的是 `app_config.load_config()`（open + yaml.safe_load）
- 职责边界：app_config=文件从哪来；models_yaml=models 段怎么变类型

**Q2：config.yaml 里 api_key 写 ${DEEPSEEK_API_KEY} 是啥意思？**
A：占位符。`_resolve_env()` 把它展开成环境变量值；密钥明文写 yaml 会进 git 泄露，所以放 `.env`（已被 .gitignore 排除）。

**Q3：paths.py 为什么用 parents[5]？**
A：`Path(__file__).resolve().parents[5]` 是从代码文件向上数 5 级到项目根：
```
config/paths.py → config(0) → agentflow(1) → harness(2) → packages(3) → backend(4) → AgentFlow(5)
```
好处：从任何目录启动都能找到 data/，不依赖"先 cd 到项目根"（P-001 路径坑的根治）。
