## 📋 结构图（两套 scheduler 并列）

### 原版 EvoFlow：`evoflow/scheduler/` = 本地工具执行引擎

```text
evoflow/scheduler/
├── task_plan.py       <task_plan> JSON 块解析 → TaskOp 列表（read/search/write/run/list_dir）
├── rules.py           classify_ops：把 ops 分三层（tier0 串行 / tier1 并行 / tier2 串行+写锁）
├── engine.py           LocalToolScheduler：按层调度执行 TaskOp
├── tool_executor.py   execute_op：真正调工具（read/search/write/run/list_dir）
├── prefetch_stream.py 索引搜索 + 并行读文件 → XML 预热上下文
├── search_follow_read.py 搜索后并行读目标文件
├── post_edit_lint.py  编辑后 lint
├── retry.py           重试
└── subagent_stream.py 子代理流式
```

**数据流**：模型输出 `<task_plan>{ops:[...]}</task_plan>` → `task_plan.parse_task_plan_from_text` 解析成 `TaskPlan` → `rules.classify_ops` 分三层 → `engine.run_async` 按层调度 → `tool_executor.execute_op` 真正执行每个 op。

### AgentFlow M5：`agentflow/scheduler/` = 定时触发器

```text
agentflow/scheduler/
├── __init__.py
├── cron.py   手写 5 字段 cron 匹配（normalize_schedule + cron_matches_at）
└── loop.py   AutomationScheduler daemon tick（扫库→命中→queue.put）
```

**数据流**：REPL 主线程创建任务落 SQLite → daemon tick 每 60s `list_active()` → `cron_matches_at` 命中 → `queue.put((task_id, prompt))` → 主线程 drain 队列执行。

> **一句话差异**：原版 `scheduler/` 调度的是「**一个 agent 计划里的一堆工具操作**」（什么时候读文件、什么时候写文件、能不能并行）；AgentFlow `scheduler/` 调度的是「**一堆定时任务什么时候该触发**」。两者都叫 scheduler，但调度对象、调度逻辑、产出完全不同。

## 💡 设计思想：原版 scheduler 是「执行引擎」不是「定时」

原版 `evoflow/scheduler/engine.py` 文件头自述「Local tool scheduler engine」——它是一个**本地工具调度执行引擎**，跟 cron / 定时**毫无关系**。核心设计：

1. **输入是 TaskPlan，不是时间**：`task_plan.py` 从模型输出文本里正则抠出 `<task_plan>...</task_plan>` JSON 块，解析成 `TaskOp` 列表。每个 op 是一个工具调用意图：`read` / `search` / `write` / `run` / `list_dir`，带 path / paths / query / content / command 等字段。
2. **三层分类规则（`rules.py`）**：`classify_ops` 把 ops 分三档——
   - **tier0（串行先跑）**：入口文件（`main.py` / `index.ts` / `app.py` / `__main__.py` / `mod.rs` 等）或配置指定的 tier0 路径，**必须先读**才能理解项目；
   - **tier1（并行跑）**：`read` / `search` / `list_dir` 这类只读 IO，可 `asyncio.gather` 并行（受 IO 信号量限流）；
   - **tier2（串行 + 写锁）**：`write` / `run` 这类有副作用的操作，全局 `asyncio.Lock` 串行，避免并发写冲突。
3. **执行引擎（`engine.py` `LocalToolScheduler`）**：`run_async(plan)` 先 tier0 串行 → 再 tier1 并行 gather → 最后 tier2 串行+写锁。每个 op 交 `tool_executor.execute_op` 真正执行，并记 `log_scheduler_invocation`。产出 `ExecutionReport`（status=ok/partial + results 列表），格式化成 XML 回喂模型。
4. **预取流（`prefetch_stream.py` + `engine.run_prefetch_async`）**：另一条线——给定 query，先 `search_index` 搜代码索引，再并行读 top-N 文件，拼成 `<prefetch_context>` XML 预热上下文给模型；还会沿依赖图（`dependency_neighbors`）扩展 hops。

**关键认知**：原版 scheduler 是「**把模型的工具调用计划最优地执行掉**」——决定哪些读操作可以并行、哪些写必须排队、入口文件要先读。它优化的是**单轮 agent 内部的工具执行效率**，不是「什么时候跑任务」。

## 📋 AgentFlow M5 scheduler 是「定时触发器」

AgentFlow `agentflow/scheduler/` 两个文件，做的是**时间维度的触发判断**：

1. **`cron.py` — 手写 5 字段 cron 匹配**：`normalize_schedule(expr)` 归一化（空/关键词/非法 → 兜底 `0 9 * * *`），`cron_matches_at(expr, dt)` 判断 dt 是否命中调度（支持 `*` `,` `-` `*/n` `a-b/n`，DOW 按 JS 约定 0=周日，dom/dow POSIX OR 语义）。零第三方依赖。
2. **`loop.py` — daemon tick 线程**：`AutomationScheduler(repo, queue, interval=60)` 起一个 daemon 线程，每轮 `_tick`：`list_active()` → 逐条 `cron_matches_at` → 分钟级去重（`_fired_minute` 内存态）→ once 型幂等（`once_fired` 落库 + 偏离目标 >120s 跳过）→ `queue.put((task_id, prompt))`。**tick 线程绝不建 agent、不碰模型**。

**关键认知**：AgentFlow scheduler 优化的是「**一堆用户预设的定时任务，到点了没有、该不该触发**」——是时间维度的触发器，没有「工具调用计划分层执行」这回事。

## 📊 差异本质对比表

| 维度 | 原版 EvoFlow scheduler（执行引擎） | AgentFlow M5 scheduler（定时触发器） |
|---|---|---|
| **本质** | `LocalToolScheduler`：把模型产出的 TaskPlan 分层执行 | `AutomationScheduler`：cron 表达式匹配 + daemon tick 入队 |
| **调度对象** | 一个 agent 计划里的 N 个工具操作（TaskOp） | SQLite 里的 N 条定时任务定义 |
| **输入** | 模型输出的 `<task_plan>` JSON 块（read/search/write/run/list_dir） | 任务行的 `schedule`（5 字段 cron 串）+ 当前时刻 dt |
| **调度逻辑** | `rules.classify_ops` 分三层：tier0 入口文件串行 → tier1 只读并行 → tier2 写/跑串行+写锁 | `cron_matches_at` 逐字段比对 minute/hour/month/dom/dow |
| **执行动作** | `tool_executor.execute_op` 真正调工具（读文件/搜代码/写文件/跑命令） | `queue.put((task_id, prompt))`——**只投递，不执行** |
| **并发模型** | `asyncio.Semaphore` 限 IO 并发 + 全局写锁 + tier1 `asyncio.gather` 并行 | `threading.Thread` daemon + 内存态 `_fired_minute` 去重 |
| **预取/预热** | `run_prefetch_async`：search_index → 并行读 → `<prefetch_context>` XML 喂模型 | 无 |
| **产出** | `ExecutionReport`（status + results）→ XML 回喂模型 | 一条入队消息 `(task_id, prompt)` |
| **是否碰模型** | 不直接碰模型，但产出是给模型看的 execution_report XML | 绝不碰模型（刻意设计） |
| **时间语义** | 无时间概念（执行快慢由 asyncio 并发决定） | 核心就是时间（cron 串 + 本地 naive 墙钟） |

## 🎯 后续对齐方向（M8+，当前不改代码）

> 本节是**方向性建议**，不是本次交付的执行项。本次只写文档。

1. **命名切割**：AgentFlow 当前 `agentflow/scheduler/` 装的是「定时触发器」。未来要移植原版那套「工具执行引擎」时，**不要塞进同一个 `scheduler/` 包**——建议另立 `agentflow/tool_dispatcher/` 或 `agentflow/plan_executor/` 之类的模块，把「时间触发」和「计划执行」两个正交概念物理分开。
2. **移植执行引擎的次序**（如果 M8+ 需要）：先 `task_plan.py`（解析模型 `<task_plan>` 输出）→ 再 `rules.py`（三层分类）→ 再 `tool_executor.py`（对接 AgentFlow 现有 tools/ 域的 read/search/write）→ 最后 `engine.py`（asyncio 调度）。`prefetch_stream.py` 依赖代码索引（`code_index/`），AgentFlow 当前没有该子系统，属于更后期的事。
3. **当前 scheduler/ 保持稳定**：`cron.py` / `loop.py` 服务 M5 定时任务需求，pytest 164 基线不动。后续演化时优先扩展执行侧（tick 命中后怎么真正跑 agent），而不是动 cron 匹配内核。
4. **不要误读原版 scheduler**：以后读原版 `evoflow/scheduler/` 源码时，记住它是「执行引擎」，别把它当「定时调度」参考。原版的定时调度在 `app/gateway/automation_runner.py`。

## ❓ Q&A / 知识点

### 1. 为什么两个项目都叫 scheduler，做的事完全不一样？

**一句话**：scheduler 这个词本身就歧义——它可以指「调度什么时候触发」，也可以指「调度一堆操作怎么执行」。原版取后者，AgentFlow 取前者。

原版 `evoflow/scheduler/engine.py` 文件头自述「Local tool scheduler engine」，它调度的对象是 tool ops（读/写/搜/跑），优化的是单轮 agent 内的工具执行并行度。AgentFlow `agentflow/scheduler/` 调度的对象是定时任务，优化的是「到点了没」。两边各自用了 scheduler 的一个义项，没对齐。

### 2. 原版 tier0/tier1/tier2 分层解决什么问题？

**一句话**：解决「并行读要尽早、串行写要不冲突、入口文件要先读」这三个约束。

- tier0（入口文件）必须先读，否则后面的搜索/编辑找不到项目骨架；
- tier1（read/search/list_dir）是只读 IO，并行能显著缩短等待；
- tier2（write/run）有副作用，全局写锁串行避免并发写冲突。
这是经典的「读写并发控制」在工具执行层的投影。AgentFlow 当前没有这层，因为 AgentFlow 的工具调用是 REPL 里一个个串行走的，还没有「批量计划一次执行」的场景。

### 3. AgentFlow loop.py 的 tick 和原版 automation_runner.py 的 tick 是一回事吗？

**一句话**：节奏像（都是 60s 一轮），但产出完全不同。

原版 `automation_runner.py` tick 命中后**直接在本进程调 LangGraph `runs.wait` 把 agent 跑完**；AgentFlow `loop.py` tick 命中后只 `queue.put` 一条消息就走，**真正执行留给主线程**。所以原版 tick 是「执行入口」，AgentFlow tick 是「通知器」。AgentFlow 这么设计是为了让 daemon 线程崩溃不拖垮 REPL，但代价是和原版 runner 的执行语义不接轨。

## ⚠️ 风险点

1. **引用原版 scheduler 时不要张冠李戴**：原版 `evoflow/scheduler/engine.py` 不是「定时调度引擎」，是「工具执行引擎」。做 M8+ 对齐时别把它的 tier 分层逻辑往 cron/loop 上套。
2. **两个 scheduler 包未来必须物理分离**：如果 M8+ 移植原版执行引擎，塞进现有 `agentflow/scheduler/` 会让「定时触发」和「计划执行」两个正交概念耦合，后续维护噩梦。
3. **本说明是方向性记录**：里面提到的移植项都是 M8+ 的事，当前 pytest 164 基线不动。
