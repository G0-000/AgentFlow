原版 `routers/models.py`（前缀 `/api`，tags=["models"]）= list_models（ModelResponse 归一化）+
get/set_primary_model + **invoke_configured_model（模型直调，返回结构化结果）** +

**M7 学什么**：`list_models` / `get_primary_model` / `set_primary_model`（读模型工厂）+

**砍什么**：cancel 里对 LangGraph 的深绑定——M7 用 agentflow 自己的
`persistence/session_run_state` + 停止语义替代（若无对应会话则返回 ok:true, cancelled:0）。

message_bus.py（InboundMessage/OutboundMessage/ResolvedAttachment + MessageBus：
inbound 队列 + outbound 订阅发布）+ manager.py（IM 快捷命令/会话索引/transcript）+

**M7 学什么**：`base.py` 的 Channel ABC + 入站消息归一化（InboundMessage，定义于
message_bus.py）+ `feishu.py` 的**入站去重（`_FeishuInboundDeduper`：msg_id TTL + content TTL 双去重）**+
文本收发最小路径（parse_inbound → 去重 → 跑 Agent → feishu_outbound_text 回发）。
**架构对齐补位（2026-10-18）**：message_bus.py（MessageBus 队列/订阅 + Inbound/OutboundMessage）与
manager.py（ChannelManager 注册 + 入站路由）按原版结构就位——多渠道扩展点存在，接第 2 个平台
（企微/Slack…）时填实现即可，不重构。
**砍什么**：卡片体系（build_*_card 系列）、文件上传/图片、slack/telegram/wecom/weixin/dingtalk

feishu 全链路改走总线（M8.1 多渠道实装时再接线）。

### 纠偏 5：原版 feishu_stream_bridge.py 是"子任务事件 → 飞书流式推送"，M7 学最小桥接

原版 `feishu_stream_bridge.py` 342 行 = `SubtaskStreamState`（子任务状态机）+ 事件分发
（task_started/running/completed/failed）+ `_push_to_feishu`（文本行 + 缩进汇总）+
单例 `get_feishu_stream_bridge` / `init_feishu_stream_bridge`。

**M7 学什么**：状态机 + 事件分发语义 + 文本行推送（不渲染卡片）。
**砍什么**：完整卡片渲染、chat_id/thread_ts 上下文联动细节（M7 只推纯文本状态行）。

### 纠偏 6：原版依赖 fastapi/uvicorn/sse-starlette/lark-oapi/websockets，M7 对齐追加

原版 `backend/pyproject.toml`：`fastapi>=0.115.0`、`uvicorn[standard]>=0.34.0`、
`sse-starlette>=2.1.0`、`lark-oapi>=1.4.0`、`websockets>=12.0`、`httpx>=0.28.0`。
agent-flow 当前只有 M6 的 langchain-mcp-adapters/ddgs/pyjwt——M7 追加这 6 个（对齐原版同款）。

**uvicorn 是什么（为什么 FastAPI 需要它）**：

```text
FastAPI（框架，定义路由/中间件/lifespan）      ← 不自己跑
uvicorn（ASGI 服务器，真正 listen 38012 端口） ← 靠它才"活"起来
```

- FastAPI 只定义"接口长什么样"，本身不监听端口；**uvicorn 是 ASGI 服务器**，
  负责接收 HTTP 请求、交给 FastAPI 处理、返回响应。M7 启动 gateway 就靠它：
  `uvicorn app.gateway.app:create_default_app --factory --host 127.0.0.1 --port 38012`。

**`[standard]` 是附加依赖包（extras）**——不带它的 uvicorn 是纯内核，只处理基础 ASGI；
带 `[standard]` 多装 4 个组件：

| 组件 | 作用 |
|---|---|
| `uvloop` | 更快的事件循环（替代 asyncio 默认 loop，性能提升） |
| `httptools` | 更快的 HTTP 解析器 |
| `websockets` | WebSocket 协议支持（后续 gateway 挂 WS 端点要用） |
| `watchfiles` | `--reload` 热重载（开发时改代码自动重启） |

**M7 为什么需要它**：
1. Gateway 必须跑起来——M8 前端登录/聊天/模型设置全走这个进程（38012）
2. 对齐原版：EvoFlow 的 pyproject 就是 `uvicorn[standard]>=0.34.0`
3. `[standard]` 里的 websockets 与 M7 飞书渠道（WS 长连接）同生态——虽然飞书 WS
   是 lark-oapi 自己连的，gateway 侧后续要做 WS 推送也有底子

**类比**：FastAPI 是"餐厅菜单"（有什么菜/怎么接单），uvicorn 是"厨房炉灶"
（真正把菜做出来端上桌）——M7 之前 CLI 直连核心层不需要它，有了 gateway 就必须配炉灶。

## 7. 场景演练：SSE 事件流与飞书消息如何流动

本节是帮助理解数据流的**模拟示例**。M7 落地前，以下接口与数据形状代表
"Gateway + 飞书渠道的最小闭环"目标形态；示例中的 `run:` / `inbound:` 表示调用方视角。

### 先看一个 run 的 SSE 事件流

```text
POST /api/langgraph/runs  →  触发一次执行
SSE GET /api/events?run_id=r_demo
  event: run.started   data: {"run_id":"r_demo","status":"running"}
```

### 再看飞书渠道的一个入站闭环

```text
飞书事件（challenge / 消息回调）进入 FeishuChannel
  └─ parse_inbound(event) → ParsedInbound（归一化 + 去 @/零宽字符）
       ├─ 重复则丢弃（_FeishuInboundDeduper.is_duplicate：msg_id TTL + content TTL 双去重）
       └─ 非重复 → on_message() 跑 Agent（thread_id 映射）→ 回发
            └─ feishu_outbound_text(text) → im.v1.message.reply 回平台
```

> ⚠️ 数据流对照：当前飞书**仍走上述内联路径**（不经过 MessageBus/ChannelManager）。

> MessageBus 队列 → dispatcher 消费 → 发布 OutboundMessage → (channel_name, account_id)
> 槽位回调回发；ChannelManager.register 注册各渠道、start_all 统一启动。总线/注册表
> 代码已就位（test_channel_bus_manager.py 8 项契约验证），接线在 M8.1 多渠道时完成。
