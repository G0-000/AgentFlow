## 2. 原版纠偏记录（必读——对齐表错位清单）

验收清单里"对齐原版 app/gateway/、app/channels/"的字面对齐，
经源码核实有以下错位（M7 照此纠偏，不整包照搬）：

### 纠偏 1：原版 gateway/ 是 100+ 文件的全量应用层，M7 只学"骨架 + 分层注册"

原版 `app/gateway/` 100+ 文件 = app.py（471 行：`create_app(defer_routers=True)` + lifespan
后台启动 + lazy singleton `__getattr__`）+ router_registry（core 29 路由 + extended 34 路由
分两批后台挂载）+ routers/（60+ 个：models 1132 行 / knowledge / browser_* / speech / collab /
a2a / meetings / eval / automation…）+ streaming/（流式镜像/续流/批处理）+ events/ + speech/ +
cancellation/ + v4/ + v4_demo/ + startup_trace/ 等。

**M7 学什么**：`app.py` 的 `create_app` + lifespan（先注册 health、yield 后后台挂其余——
early ready 语义）+ `router_registry.py` 的分层注册模式（core 先挂、extended 后台挂）+
`LazyLangGraphMount` 的 `/api/langgraph` 挂载语义。
**砍什么**：knowledge/knowledge_owned/browser/speech/collab/automation/a2a/meetings/eval/apps/
organizations 等全部 extended 重路由（`knowledge_owned` 是 2026-10-11 原版新增的自建知识中心路由，
M7 不学）；streaming 全家桶（流式镜像、续流、SSE 批处理）——M7 只留最小 SSE。
原版同日还在 evopanel 侧新增 `sse-frame-batch.js`（SSE 帧批处理，前端 M8 域），M7 仅作后续参考。

### 纠偏 2：原版 routers/models.py 1132 行是"模型管理 CRUD + 连接测试"，M7 学读操作子集

原版 `routers/models.py`（前缀 `/api`，tags=["models"]）= list_models（ModelResponse 归一化）+
get/set_primary_model + **invoke_configured_model（模型直调，返回结构化结果）** +
create/update/delete_model（写操作）+ probe_embedding_model + test_model_connection +
tokenizer_status + openai_compat 直连测试 + dashscope 兜底。

**M7 学什么**：`list_models` / `get_primary_model` / `set_primary_model`（读模型工厂）+ 
`invoke_configured_model`（模型直调的最小形状：messages → text 提取 → 响应）。
**砍什么**：create/update/delete（模型写操作）、probe/test_connection/tokenizer/openai_compat/
dashscope_fallback（连接测试与兼容层——M7 不做模型运维）。

### 纠偏 3：原版 routers/runs.py 的 cancel 是"全局取消"，M7 学 list + cancel 最小语义

原版 `routers/runs.py`（前缀 `/api/langgraph/runs`）= `list_runs`（当前是**简化空实现**，
返回空 runs + pending/running 计数）+ `cancel_all_runs`（**真实实现**：`list_all_active_sessions`
+ 信号量 10 并发 `stop_session_execution`，全局取消并落库、返回 cancelled_count）。

**M7 学什么**：路由前缀挂 `/api/langgraph/runs`（走 LangGraph 同域）+ list 的空实现形状
（不编造数据）+ cancel 的**并发取消语义**（会话扫描 → 有界并发 stop → 汇总结果）。
**砍什么**：cancel 里对 LangGraph 的深绑定——M7 用 agentflow 自己的
`persistence/session_run_state` + 停止语义替代（若无对应会话则返回 ok:true, cancelled:0）。

### 纠偏 4：原版 channels/ 是 20+ 文件多渠道全家桶，M7 只学"1 个渠道的最小闭环"

原版 `app/channels/` = base.py（Channel ABC：start/stop/send + send_file + _make_inbound）+
message_bus.py（InboundMessage/OutboundMessage/ResolvedAttachment + MessageBus：
inbound 队列 + outbound 订阅发布）+ manager.py（IM 快捷命令/会话索引/transcript）+ 
**feishu.py 3232 行**（WS 长连接 + 入站去重 + 卡片体系 + 文件上传 + 流式更新）+ 
slack/telegram/wecom/weixin/dingtalk + store/service/goal/。

**M7 学什么**：`base.py` 的 Channel ABC + `message_bus.py` 的队列/订阅模型 +
`feishu.py` 的**入站去重（`_FeishuInboundDeduper`：msg_id TTL + content TTL 双去重）**+
WS 连接循环（`_feishu_ws_connect_loop`）+ 文本收发最小路径。
**砍什么**：卡片体系（build_*_card 系列）、文件上传/图片、slack/telegram/wecom/weixin/dingtalk
（5 个渠道）、manager 的会话索引与 transcript 大部（M7 只留注册 + 入站路由）。

### 纠偏 5：原版 feishu_stream_bridge.py 是"子任务事件 → 飞书流式推送"，M7 学最小桥接

原版 `feishu_stream_bridge.py` 342 行 = `SubtaskStreamState`（子任务状态机）+ 事件分发
（task_started/running/completed/failed）+ `_push_to_feishu`（文本行 + 缩进汇总）+
单例 `get_feishu_stream_bridge` / `init_feishu_stream_bridge`。

**M7 学什么**：状态机 + 事件分发语义 + 文本行推送（不渲染卡片）。
**砍什么**：完整卡片渲染、chat_id/thread_ts 上下文联动细节（M7 只推纯文本状态行）。

### 纠偏 6：原版依赖 fastapi/uvicorn/sse-starlette/lark-oapi/websockets，M7 对齐追加

原版 `backend/pyproject.toml`：`fastapi>=0.115.0`、`uvicorn[standard]>=0.34.0`、
`sse-starlette>=2.1.0`、`lark-oapi>=1.4.0`、`websockets>=12.0`、`httpx>=0.28.0`。
agent-flow 当前只有 M6 的 langchain-mcp-adapters/ddgs/pyjwt——M7 追加这 6 个（对齐原版同款）。

## 7. 场景演练：SSE 事件流与飞书消息如何流动

本节是帮助理解数据流的**模拟示例**。M7 落地前，以下接口与数据形状代表
"Gateway + 飞书渠道的最小闭环"目标形态；示例中的 `run:` / `inbound:` 表示调用方视角。

### 先看一个 run 的 SSE 事件流

```text
POST /api/langgraph/runs  →  触发一次执行
SSE GET /api/events?run_id=r_demo
  event: run.started   data: {"run_id":"r_demo","status":"running"}
  event: run.event     data: {"run_id":"r_demo","kind":"tool_call","span_name":"ddgs.search"}
  event: run.completed data: {"run_id":"r_demo","status":"success","duration_ms":1234}
```

断流时客户端重连（Last-Event-ID / 重新订阅），服务端从最近事件续推——这就是
`test_sse_ui_stream_resilience.py` 验证的韧性语义（M7 只做"续收不炸"，不做镜像/批处理）。

### 再看飞书渠道的一个入站闭环

```text
飞书 WS 长连接收到消息
  └─ FeishuChannel._on_inbound(msg)
       ├─ _FeishuInboundDeduper.is_duplicate(msg_id, chat_id, text)  → 重复则丢弃
       ├─ 非重复 → MessageBus.publish_inbound(InboundMessage)
       └─ manager 路由 → agentflow 会话执行 → OutboundMessage → FeishuChannel.send(text)
```

同一 `msg_id` 在 TTL 内重复推送、或同一 `chat_id` 短时相同文本，都只处理一次——
这就是 `test_feishu_inbound_dedup.py` 验证的契约。

### 这条演练能证明什么

- Gateway 的 health/核心路由/SSE 数据形状是什么样；飞书渠道的消息闭环怎么走。
- 测试覆盖：健康检查、模型读接口、runs 最小语义、SSE 断流韧性、会话并发、飞书去重。
- **不证明**：模型写操作/连接测试、卡片与文件上传、多渠道（slack/telegram/wecom…）——
  均不在 M7 范围；自动化的流式镜像与续流也留待后续。
