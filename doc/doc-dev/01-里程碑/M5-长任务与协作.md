# M5 —— 长任务与协作（Plan/Goal 引擎 + Automation 定时调度）

> **一句话目标**：让 Agent 从"一次对话干完"升级到"接复杂长活"——
> 先**出步骤计划**（JSON steps），再**逐步执行**（每步有状态），
> 杀进程后 `--thread` 能**从断点续跑**，完工自动出**汇总报告**；
> 另外能挂**定时任务**（"每天 9 点检查"，验收演示用"每分钟 echo"），到点自己触发并留记录。
> 前置：M4 验收 5/5 已过（子代理并行 ≤3 + 沙箱审计，基线 64 passed）。

## 1. M5 做什么（用户视角）

| 能力 | 之前（M4） | 之后（M5） |
|---|---|---|
| 复杂任务 | 主 Agent 一把梭，上下文里边走边看 | **先出计划**："写一篇 3 章报告"→ Agent 先吐 JSON 步骤计划（ref/依赖），拓扑校验通过才开干 |
| 执行推进 | 无步骤概念 | **逐步执行**：steps 按依赖拓扑排序逐个跑，每步 pending→executing→completed，落库可查 |
| 中断恢复 | 对话能 `--thread` 续聊，但长任务跑一半杀进程=重头来 | **断点续跑**：goal 行持久化 current_step/completed_steps，重启 `--thread` 从下一步接着跑，已完成步不重跑 |
| 完工交付 | Agent 把话说完就结束 | **结果汇总**：全部 steps 完成 → goal 行写 summary/outcome，REPL 打印最终报告 |
| 定时任务 | 无 | **automation**：`agentflow automation create --schedule "每分钟"` → 后台 tick 线程每分钟扫库，到点把 prompt 投队列、主循环触发执行、写 run 记录 |
| 回归 | 64 passed | 64 passed 不减 + M5 新增测试全绿 |

## 2. 🔁 原版纠偏记录（4 条，必读——原"对齐表"是错的，M5 照此纠偏）
> 验收清单里"对照原版 plans/、scheduler/、goal_graph"的字面对齐，经源码核实**全是错位**。以下 4 条是 M5 的事实基线，写代码/写文档照此执行，不再参照旧对齐表。

### 纠偏 1：原版 `plans/` 是"套餐绑定"，不是计划模块

**原版真相**：`evoflow/plans/`（types/service/resolver/catalog）实为**第三方套餐绑定 / 密钥路由**模块——火山 Agent Plan BYOK，做"套餐 → API key 路由"，与"长任务计划"毫无关系。

**M5 结论**：整个砍掉，**不学**。

**真正的计划模型在 `evoflow/collab/`**（M5 的 `plans/` 学它，不学原版 plans/）：

| 学什么 | 出处 | 内容 |
|---|---|---|
| TaskStatus 枚举 | `collab/models.py` | 8 态：pending / planning / planned / executing / paused / completed / failed / cancelled |
| PlanStep 结构 | `collab/plan_task_storage.py` | dict：`ref` / `short_name` / `description` / `depends_refs[]` / `status` |
| 挂主任务行 | `collab/plan_task_storage.py` | `plan_goal` + `plan_steps_json` 挂在主任务行上 |
| 状态迁移白名单 | `collab/state_transitions.py` | `ALLOWED_TRANSITIONS` 迁移表 |
| 执行迁移器 | `collab/task_state_service.py` | begin_planning / begin_execution / complete_step / complete_task |
| 7 阶段生命周期 | `collab/execution_lifecycle.py` | planning→plan_ready→awaiting_authorization→authorized→executing→paused→done；含 `user_execution_start_intent(text)` 裸文本识别"开始执行" |

**砍掉的**：`collab/` 其余 50+ 文件（supervisor / peer / org / App / 推送 / 观测）是 **M7 组织级能力**，M5 不碰。

### 纠偏 2：原版 `scheduler/` 是"工具批量执行器"，定时系统在 automation 三处

**原版真相**：`evoflow/scheduler/`（engine/rules/task_plan/tool_executor…）实为**本地工具批量执行器**——tier0 串行 → tier1 `asyncio.gather` 并发 → tier2 串行写锁，与 cron 定时**毫无关系**。

**M5 结论**：整个砍掉，**不学**。

**真正的定时系统在三处**（M5 的 `scheduler/` 学它们）：

| 学什么 | 出处 | 内容 |
|---|---|---|
| 两表持久化 | `persistence/automation_repositories.py` | `automations` + `automation_runs` |
| tick 循环 | `app/gateway/automation_runner.py` | `DEFAULT_INTERVAL_SECONDS=60`：扫 active → cron 匹配 → 触发 → 写 run |
| 手写 cron 匹配 | `admin/automation_schedule.py` | **cron 5 字段**：支持 `*/`、`,`、`-`；DOW 按 JS 0=周日；关键词 `@daily`/每天/daily 归一化；兜底默认 `FREQ=DAILY;BYHOUR=9`（即 `0 9 * * *`） |

**automation/ 包去留（决策 D1）**：原版 `automation/` 仅剩 `output_paths.py`（交付物落盘路径，可选）→ **M5 不建 automation 包**，定时能力全部落在 `scheduler/`（cron.py + loop.py）+ `persistence/automation_repositories.py`。

### 纠偏 3：原版 goal_graph 是"伪循环"，真闭环在 middleware 钩子

**原版真相**（三层拆开看）：

| 层 | 原版文件 | 事实 |
|---|---|---|
| goal_graph.py | `agents/goal/goal_graph.py` | **伪循环**：controller 路由无条件回 END；`langgraph_sdk` 依赖仅是类型注解（goal_graph:10/207）+ main_agent_runner 远程流调用 |
| 真闭环 | `agents/goal/goal_auto_continue_middleware.py` | 在 `after_model` 钩子里 `jump_to=model/end` 实现续跑 |

**M5 结论**：砍 goal_graph 与 middleware 钩子，**改外部 while 循环**（GoalEngine，同步 invoke，对齐 CLI 主循环）。

**保留学的**（按文件拆）：

| 学什么 | 出处 | 内容 |
|---|---|---|
| 首转/续跑提示词 | `goal_runtime.py` | `build_goal_mode_preamble`（首转）/ `build_continue_nudge`（续跑） |
| 原子状态写 | `goal_runtime.py` | `patch_goal_state`：原子 UPDATE，`WHERE goal_status IN ('active','paused')` 防终态覆盖 |
| 判定模型 | `goal_reply_interpreter.py` | 输出 JSON `{verdict: continue|complete, summary, reason}`；**等用户回答也判 continue** |
| 判定表 | `goal_controller.py` | complete = completed / 超时 / 步数上限 / `<completed>` 标签 / verdict=complete；continue = 默认；**wait_user = legacy 死路，砍** |
| 字段裁剪 | `goal_state.py` | 留 12 字段：goal_id/goal_text/goal_status/status/current_step/max_steps/completed_steps/remaining_steps/last_error/stop_reason/summary/outcome；**messages 砍掉，交给 checkpointer** |

**运行守卫表**（来自 auto_continue，M5 裁剪为 4 条）：

| # | 守卫 | 行为 |
|---|---|---|
| 1 | 空回复 | 按 retry_limit 重试，超限 → paused |
| 2 | 步数上限 | current_step ≥ max_steps → complete |
| 3 | fallback streak ≥ 3 | 判定解析连续失败 3 次 → 熔断 paused |
| 4 | 异常 | 任何 invoke/judge 异常 → paused |

**注意**：原版 goal **无"步骤计划"结构**——"计划→逐步执行"是 M5 新增能力，原版无参照，按 collab plan 模型**自设计**。

### 纠偏 4：原版点名的三个测试全仓不存在

**原版真相**：EvoFlow 全仓仅 **8 个 test_*.py**；M5-验收清单点名的 `test_app_rollup.py` / `test_plan_subtask_depends_on_chain.py` / `test_goal_service_persistence.py` **不存在**；M5 相关只有 `_test_automation.py`，且是 `main()` 脚本、非 pytest 用例。

**M5 结论**：测试断言**按源码行为反推** + 按 agentflow 既有测试规范自写。

**agentflow 测试规范（自写必须遵循）**：

| 规范项 | 要求 |
|---|---|
| 组织 | 无 conftest、平铺函数 |

### 4.1 🔗 完整调用链（文件 · 函数 · 参数 · 输出；签名级，代码阶段照做）

```text
【A. 长任务 --goal 入口】cli/main.py
  main()
  ├─ 装配: goal_repo=GoalRepository(db_path=db_path)
  │        auto_repo=AutomationRepository(db_path=db_path)
  │        q=queue.Queue(); scheduler=AutomationScheduler(auto_repo,q,interval=60)
  │        scheduler.start()                       ← daemon 线程，detach
  │        engine=GoalEngine(agent, model, goal_repo)
  ├─ thread_id = args.thread or 新生成；sessions.create(thread_id)
  ├─ 断点恢复: goal_repo.get_active_by_thread(thread_id)
  │    → status ∈ {planning,planned,executing,paused} ? engine.resume(thread_id)
  └─ if args.goal: engine.start(thread_id, goal_text=args.goal)
        │
        ▼
【B. 计划生成】agents/goal/goal_loop.py — GoalEngine
  start(thread_id: str, goal_text: str, max_steps: int = 12) -> None
  ├─ goal_id = "g_" + os.urandom(6).hex()
  ├─ goal_repo.create(goal_id, thread_id, goal_text,
  │                   goal_status="planning", plan_steps_json="[]",
  │                   max_steps=max_steps, completed_steps=0)
  ├─ preamble = goal_prompts.build_goal_mode_preamble(goal_text)
  │     （要求模型输出严格 JSON: {"steps":[{"ref":"s1","short_name":...,
  │        "description":...,"depends_refs":[]}]}）
  ├─ resp = agent.invoke({"messages":[HumanMessage(preamble)]},
  │                       config={"configurable":{"thread_id":thread_id}})
  ├─ last_ai_text = resp["messages"][-1].content
  ├─ steps = plans/types.parse_steps_json(last_ai_text)  ← 容错截取首个 {...}
  │     ├─ 解析失败 → goal_repo.patch(goal_id, status="failed",
  │                                   last_error="plan json 解析失败"); 打印退出
  │     └─ 成功 → resolver.topo_sort(steps)
  │           ├─ PlanCycleError/未知ref/重名 → status="failed" + last_error
  │           └─ OK → goal_repo.update_plan(goal_id,
  │                plan_steps_json=json.dumps([asdict(s)...]), status="planned")
  └─ 自动授权（不等用户）: goal_repo.patch(goal_id, status="executing")
        │
        ▼
【C. 逐步执行】goal_loop.py（每步一轮）
  _run(thread_id, goal) -> None
  while True:
    step = plans/resolver.next_ready_step(steps)
      → PlanStep(status=pending 且 depends_refs 全部 completed) | None
    if step is None:  ← 全部走完
      goal_repo.complete_goal(goal_id, summary=聚合各步结果, outcome="done")
      break
    # 守卫①步数上限
    if goal.completed_steps >= goal.max_steps: → paused, stop_reason="max_steps"
    goal_repo.begin_step(goal_id, current_step=step.ref,
                         plan_steps_json=标记该步 executing)
    nudge = goal_prompts.build_continue_nudge(step)
      （"执行步骤 {ref}: {short_name} — {description}。完成后请用
        <completed> 标签收尾。"）
    resp = agent.invoke({"messages":[HumanMessage(nudge)]}, config thread_id)
    text = last_ai_text(resp)
    # 守卫②空回复
    if not text.strip(): retry += 1; retry>=2 → paused; continue
    verdict = goal_judge.judge_last_reply(model, text)
      → {"verdict":"continue"|"complete", "summary":..., "reason":...}
      （JSON 解析失败 → verdict="continue" + fallback_streak+1）
    # 守卫③熔断
    if fallback_streak >= 3: → paused, stop_reason="judge_fallback"
    if verdict == "complete" or "<completed>" in text:
      steps[ref].status="completed"
      goal_repo.complete_step(goal_id, current=ref, completed_steps+=1,
                              plan_steps_json=回写)
    else:  # continue：下一步自然由 while 下一圈捡起
      pass
        │
        ▼
【D. 中断恢复】goal_loop.py
  resume(thread_id: str) -> None
  ├─ g = goal_repo.get_active_by_thread(thread_id)   ← SQL 定位未完成任务
  ├─ steps = json.loads(g.plan_steps_json)          ← 从 DB 恢复步骤数组
  ├─ next = next_ready_step(steps)                  ← 已 completed 的步自动跳过
  │     （checkpointer 已按 thread_id 恢复 messages，不重放历史）
  └─ _run(thread_id, g)  ← 从 next 继续，已完成步 0 次 invoke
        │
        ▼
【E. 定时触发链】scheduler/loop.py → cli/main.py
  AutomationScheduler.__init__(repo, queue, interval=60)
  start() → threading.Thread(target=self._loop, daemon=True).start()
  _loop(): while self._running:
      self._tick(); time.sleep(self.interval)
  _tick(now=datetime.now()):
    for a in repo.list_active():           ← status='active'
      if not cron_matches_at(a.schedule, now): continue
      if a.task_id in self._fired_minute and
         self._fired_minute[a.task_id] == now.strftime("%Y%m%d%H%M"): continue
         ↑ R2 分钟级去重：同一分钟 tick 漂移重复命中只入队一次
      if a.schedule_type == "once" and (a.once_fired or
         abs(_parse(a.scheduled_at)-now) > timedelta(seconds=120)): continue
      self._fired_minute[a.task_id] = 该分钟
      self._queue.put((a.task_id, a.prompt))   ← 只投递，不执行
  REPL 每轮 input() 之后:
    while True:
      try: task_id, prompt = q.get_nowait()
      except queue.Empty: break
      run_id = auto_repo.start_run(task_id)
      print(f"⏰ 定时触发: <name>")
      try:
        out = agent.invoke({"messages":[HumanMessage(prompt)]},
              config={"configurable":{"thread_id": f"auto-{task_id}"}})
        auto_repo.finish_run(run_id, status="success", output=text(out),
                             duration_seconds=...)
      except Exception as e:
        auto_repo.finish_run(run_id, status="failed", error=str(e)[:300])
      auto_repo.touch_last_run(task_id, last_status=..., run_count+=1,
                               once_fired=1 if once)
```

## 5. 🗄️ 持久化表 DDL（进 `persistence/schema.py` 的 SCHEMA_SQL，命名定稿）

> **命名决策（定稿）**：agentflow 既有表 `sessions / session_messages / memories / knowledge_docs / knowledge_chunks / sandbox_audit` **一律无 `evoflow_`/`agentflow_` 前缀**。M5 对齐此风格 → 表名 `goals` / `automations` / `automation_runs`（不带前缀）。列按研究 shard 裁剪。

```sql
-- 长任务表（M5）：一行 = 一个长任务尝试（goal + 步骤计划 JSON 同行）
CREATE TABLE IF NOT EXISTS goals (
    goal_id          TEXT PRIMARY KEY,           -- g_ + urandom(6).hex()
    thread_id        TEXT NOT NULL,              -- 归属会话（--thread 恢复定位键）
    goal_text        TEXT NOT NULL,              -- 用户原始长任务描述
    goal_status      TEXT NOT NULL DEFAULT 'pending',
        -- pending/planning/planned/executing/paused/completed/failed/cancelled
    current_step     TEXT NOT NULL DEFAULT '',   -- 正在执行的 step.ref（断点坐标）
    plan_steps_json  TEXT NOT NULL DEFAULT '[]', -- JSON 数组[PlanStep]（含每步 status）
    max_steps        INTEGER NOT NULL DEFAULT 12,
    completed_steps  INTEGER NOT NULL DEFAULT 0,
    last_error       TEXT NOT NULL DEFAULT '',
    stop_reason      TEXT NOT NULL DEFAULT '',   -- max_steps/judge_fallback/...
    summary          TEXT NOT NULL DEFAULT '',   -- 最终汇总报告（complete 时写）
    outcome          TEXT NOT NULL DEFAULT '',   -- done/failed/...
    created_at       TEXT NOT NULL,
    updated_at       TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_goals_thread ON goals (thread_id);
CREATE INDEX IF NOT EXISTS idx_goals_status ON goals (goal_status);

-- 定时任务定义表（M5）：一行 = 一条 automation
CREATE TABLE IF NOT EXISTS automations (
    task_id        TEXT PRIMARY KEY,             -- t_ + urandom(6).hex()
    name           TEXT NOT NULL DEFAULT '',
    prompt         TEXT NOT NULL,                -- 到点投递的提示词
    schedule       TEXT NOT NULL,                -- 归一化后 cron 5 字段 "m h dom mon dow"
    schedule_type  TEXT NOT NULL DEFAULT 'recurring',  -- recurring | once
    scheduled_at   TEXT,                         -- once 型目标时间（ISO）
    status         TEXT NOT NULL DEFAULT 'active',     -- active | paused
    once_fired     INTEGER NOT NULL DEFAULT 0,
    last_run       TEXT,
    last_status    TEXT NOT NULL DEFAULT '',
    run_count      INTEGER NOT NULL DEFAULT 0,
    created_at      TEXT NOT NULL,
    updated_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_automations_status ON automations (status);

-- 定时任务执行历史表（M5，M5 唯一保留的事件历史）
CREATE TABLE IF NOT EXISTS automation_runs (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    task_id          TEXT NOT NULL,
    run_id           TEXT NOT NULL,
    started_at       TEXT NOT NULL,
    finished_at      TEXT,
    status           TEXT NOT NULL DEFAULT 'running',  -- running|success|failed
    output           TEXT NOT NULL DEFAULT '',
    error            TEXT NOT NULL DEFAULT '',
    duration_seconds REAL
);
CREATE INDEX IF NOT EXISTS idx_automation_runs_task ON automation_runs (task_id);
```

> 线程模型（P-018）：`GoalRepository(db_path=...)` / `AutomationRepository(db_path=...)` 都走 `BaseRepository` 的 db_path 模式——主线程用主线程连接，scheduler daemon 线程首次 SQL 时由 `threading.local` 自建连接（WAL 模式读写不互斥）。**tick 线程绝不持主线程注入的 conn**。

## 6. ⌨️ CLI 装配与 REPL 集成（定稿）

**子命令族**（`argparse` subparsers；无子命令 = REPL 默认行为）：

| 命令 | 作用 | 关键参数 |
|---|---|---|
| `agentflow` | REPL 对话（现状） | `--thread <id>` 续会话/续长任务；`--goal "<长任务>"` 启动后先跑 GoalEngine 再进 REPL |
| `agentflow automation list` | 列全部定时任务（id/name/schedule/status/run_count/last_run） | — |
| `agentflow automation create` | 建任务 | `--name`、`--prompt`（必填）、`--cron "*/1 * * * *"` **或** `--schedule "每天9点"`（二选一；后者经 `normalize_schedule` 归一）；`--once` 时配 `--at "2026-10-03T09:00:00"` |
| `agentflow automation pause <id>` / `resume <id>` | status 迁移 active↔paused | — |
| `agentflow automation delete <id>` | 删任务（连同 runs 历史保留，不级联删） | — |

**REPL 集成（改动点最小化）**：
1. `main()` 装配末尾：建 `q=queue.Queue()` → `AutomationScheduler(auto_repo, q).start()`；启动信息增打 `定时: N 条 active（tick 60s）`。
2. `while True` 对话循环内，**每轮 `input()` 拿到用户输入之前**，先非阻塞 `drain q`（见调用链 E）：命中的任务直接在主线程 `agent.invoke`（独立 `thread_id=f"auto-{task_id}"`，与用户会话隔离），打印触发与结果，写 run 记录。scheduler 线程永不触碰 agent/模型。
3. `--thread <id>` 启动：装配完先 `goal_repo.get_active_by_thread(thread_id)`，命中未完成任务则 `GoalEngine.resume()`——恢复打印 `[恢复] 长任务继续：第 {completed_steps+1}/{max_steps} 步`，再进 REPL。
4. `--goal "<text>"`：先 `engine.start()`（计划→逐步→汇总报告，全程打印），完成后照常进 REPL；中途 Ctrl+C → goal 行留在 executing/paused，下次同 `--thread` 可续。

## 8. ⚠️ 风险点与对策

| # | 风险 | 对策（定稿） |
|---|---|---|
| R1 | **判定模型失败死循环**：judge 解析 JSON 失败 / 模型一直说 continue 不收尾 | fallback_streak≥3 → goal 置 `paused`（熔断，不是 completed），用户可 `--thread` 手动收尾；硬上限 `max_steps=12` 双保险 |
| R2 | **cron 每分钟触发一次以上**：tick 间隔 60s 漂移，同一分钟边界扫两次 → recurring 任务重复入队 | scheduler 内存 `_fired_minute: dict[task_id→"YYYYMMDDHHM"]`，同一分钟同一任务只入队一次；once 型双保险 `once_fired=1` 落库幂等 |
| R3 | **`--thread` 恢复时 goal 状态(SQL) 与 checkpointer 消息(图状态) 不一致**：杀进程可能发生在"step 已标 completed 但消息未落"或反之 | 写入顺序固定：**先 `agent.invoke` 返回（checkpointer 已在 invoke 内落完消息）→ 再 `complete_step` 写 SQL**。恢复以 SQL 的 completed_steps/current_step 为坐标，checkpointer 只管消息历史；二者偏差最坏是重跑最后一步（幂等 nudge，可接受） |
| R4 | **后台 tick 线程 SQLite 跨线程报错**（P-018 复发） | repo 一律 `db_path=` 构造（线程本地连接）；tick 线程只做 SELECT + 写 run 记录，**绝不共享主线程 conn**；WAL 模式下读不阻塞写 |
| R5 | **M2 已有 `plan` 工具（自由文本 dict）与 M5 结构化计划混淆** | 两者并存不合并：M2 `plan` 工具=对话内随手笔记；M5 `plans/`=goal 引擎的结构化步骤机（DB 持久化）。goal 流程由 preamble 引导主 agent 直接吐 JSON，**不经过 M2 plan 工具** |
| R6 | **automation 触发跑模型时阻塞 REPL**：主线程 drain 到任务即 invoke，期间用户无法输入 | M5 接受（单线程 CLI）；run 执行打印进度提示；长任务自动化留 M6 后台化 |

## 11. 📝 代码实现接线说明（2026-10-02 代码落地时补充，与上文定稿同权）

> 两域代码（核心域 plans/goal/collab/goals 表 + 集成域 scheduler/automation/cli）已按上文定稿落地。以下 5 处为落地时明确的接线细节，不改变上文任何签名：

1. **service 与 repo 分层**：`GoalEngine.__init__(agent, model, goal_repo, service=None)`——service 缺省时内部自动建 `GoalStateService(goal_repo)`。goal_loop 永远经 **service** 走状态迁移（服务层校验 ALLOWED_TRANSITIONS 守卫，非法迁移抛 `GoalStateTransitionError`，仅 service.py 导出），repo 只做持久化原语。
2. **repo 参数名**：`begin_step(goal_id, current_step=ref, plan_steps_json=...)` / `complete_step(goal_id, current_step=ref, completed_steps+=1, plan_steps_json=...)`（参数名 `current_step` 与列名一致；`update_plan(goal_id, plan_steps_json, status)` 保持位置序）。
3. **verdict=continue 语义落法**：步 status 回写 pending，下一圈 while 重新捡起同一步 nudge；连续 continue 累计 `fallback_streak≥3` → 熔断 paused（R1 双保险成立；judge 解析失败天然 verdict=continue，自动计入熔断）。
4. **resume 语义**：被杀时处于 executing 的行**不做迁移**（只有 paused→executing 走 resume_task），并把 plan_steps_json 中残留 executing 的步重置 pending——即 R3"最坏重跑最后一步"，保证恢复时下一步状态机合法。
5. **cli/main.py 的 GoalEngine 导入**：规范路径 `from agentflow.agents.goal.goal_loop import GoalEngine`；落地代码为跨 shard 稳健性保留了 try/except 双路径（回退路径 `agentflow.goal.goal_loop` 实际不存在，永不命中）。
