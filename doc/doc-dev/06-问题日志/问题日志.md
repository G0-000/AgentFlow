## 已记录问题

### P-001：cd 路径旧名报错（M0）
- **现象**：`cd /Users/main/AegentFlow/backend` → No such file or directory
- **根因**：项目目录已从 `AegentFlow` 改名为 `AgentFlow`
- **解法**：命令前先 `ls` 确认真实路径
- **教训**：路径错比命令错更隐蔽

### P-002：uv sync 找不到 pyproject.toml（M0）
- **现象**：`error: No pyproject.toml found in current directory`
- **根因**：在空目录/没有 pyproject 的地方执行
- **解法**：pyproject.toml 在哪，uv sync 就在哪执行
- **教训**：`uv sync` 的位置由 pyproject 位置决定

### P-003：workspace 成员缺失（M0）
- **现象**：`evoflow-harness ... is not a workspace member`
- **根因**：只 copy 了 backend/pyproject.toml，没建 packages/harness（workspace 成员）
- **解法**：双包结构必须配套建齐（members + 实际目录）
- **关联**：[ADR-001](../03-决策记录/ADR-001-workspace双包.md)

### P-004：uv 命令找不到（M0）
- **现象**：`uv: command not found`
- **根因**：uv 装在 `~/.local/bin`，脚本环境 PATH 不含它
- **解法**：`export PATH="$HOME/.local/bin:$PATH"` 或使用完整路径

### P-005：langgraph-prebuilt 版本冲突（M1）
- **现象**：`ImportError: cannot import name 'ExecutionInfo' from 'langgraph.runtime'`
- **根因**：约束过宽 → prebuilt 1.0.13 需新 API，langgraph 1.0.9 没有
- **解法**：对齐原版 uv.lock：`langgraph-prebuilt==1.0.8`
- **教训**：原版 lock 是版本权威；关键包用 `==` 锁定
- **关联**：[ADR-002](../03-决策记录/ADR-002-依赖版本对齐原版.md)

### P-006：api_key 空 → Missing credentials（M1）
- **现象**：`Missing credentials. Please pass an api_key`
- **根因**：config.yaml 的 `${ZHIPU_API_KEY}` 未展开——.env 没建或没写
- **解法**：项目根建 `.env`（DEEPSEEK_API_KEY=xxx），cli 的 load_dotenv() 自动读
- **注意**：`.env` 已被 .gitignore 排除（密钥不入库）

### P-007：模型名/地址错误（随时）
- **现象**：`model not found` / 401
- **根因**：config.yaml 的 base_url / model 与平台不符
- **解法**：DeepSeek=`https://api.deepseek.com/v1` + `deepseek-chat`；智谱=`https://open.bigmodel.cn/api/paas/v4` + `glm-4.7-flash`

### P-012：402 Insufficient Balance（M1 验收遇阻）
- **现象**：真实对话报 `Error code: 402 - Insufficient Balance`
- **根因**：key 有效、地址/配置全对（请求已到达 DeepSeek 服务器），但**账户余额为 0/欠费**
- **解法 A（付费）**：platform.deepseek.com 充值 → 重跑 `uv run agentflow`
- **解法 B（免费，推荐）**：DeepSeek API 无免费额度（网页版才免费）；**智谱 GLM-4.7-Flash API 全免费**——config.yaml 已切到智谱（provider=zhipu / glm-4.7-flash），.env 填 ZHIPU_API_KEY 即可零成本验收
- **教训**：402 ≠ 认证错误（401 才是 key 问题）；代码链路已全通，只差钱/换免费模型

### P-013：langchain 1.2.x 消息角色是 `ai` 不是 `assistant`
- **现象**：验收脚本 `[m for m in result['messages'] if m.role == 'assistant' and m.content]` 返回空 → IndexError
- **根因**：langchain 1.2.x 里 AI 消息 `type='ai'`、`role` 属性返回 `'ai'`（不再是 `'assistant'`）
- **解法**：提取回复**不依赖 role**——直接取 content 非空的最后一条消息
- **影响**：AgentFlow 的 cli/main.py 用 `chunk.get('messages')` 流式打印 content，不依赖 role，**CLI 不受影响**；只影响验收/测试脚本的提取写法
- **教训**：读消息字段用 `type`/`content`，别用 `role` 精确匹配

### P-014：CLI 报“缺少模型配置”——config.yaml 路径依赖启动目录
- **现象**：在 backend/ 下 `uv run agentflow` 报“缺少模型配置”，但用绝对路径加载配置却正常
- **根因**：`load_config()` 默认找 `./config.yaml`（相对**当前工作目录**）；从 backend/ 启动时 backend/config.yaml 不存在 → models=None → CLI 误报缺配置
- **解法**：CLI 显式传 `project_root / "config.yaml"`（`Path(__file__).resolve().parents[5]` 向上找项目根）——对齐原版思想（原版多处用 `Path(__file__).resolve().parents[N] / "config.yaml"`）
- **教训**：配置定位不要依赖“从哪个目录启动”，要用代码文件位置向上定位项目根

### P-015：智谱 GLM-4.7-Flash 高峰限流（code 1305）
- **现象**：模型调用卡住/超时；curl 直测返回 `{"error":{"code":"1305","message":"该模型当前访问量过大，请您稍后再试"}}`
- **根因**：免费模型无付费兜底，高峰期服务端限流（时段性波动：早前 invoke 成功，后失败）
- **解法**：① 错峰重试；② CLI 对话循环已加 try/except 容错（限流时报友好提示不崩 CLI，`# noqa: BLE001`）；③ **模型层加 timeout=60 超时兜底**（ChatOpenAI 构造期生效，挂起 60s 抛 APITimeoutError → CLI 接住，不再"半天不回"）
- **备选方案（实测有效）**：智谱免费文本模型不止 4.7——**GLM-4.5-Flash 也免费**（128K 上下文），4.7 限流时把 config.yaml 的 model 改成 `glm-4.5-flash` 即可绕过（2026-09-28 实测 HTTP 200 正常回复）
- **教训**：免费 API 不稳定是常态——代码要能优雅失败；验收时若遇 1305/1302 换个时段再跑，或切 4.5-Flash

### P-016：CLI 流式"打字不出内容"（两个根因叠加）
- **现象**：`uv run agentflow` 输入问题后 `Agent >` 空白，无回复无报错；非流式（invoke）却正常
- **根因①（供应商）**：智谱 GLM-4.5/4.7-Flash 是 **thinking 模型**，默认开启思维链——**流式时内容在 `delta.reasoning_content`，不在标准 `delta.content`**，langchain-openai 只读 content → 全空
  - 验证：curl 直测 stream 看到 `{"delta":{"reasoning_content":"..."}}`；加 `"thinking":{"type":"disabled"}` 后恢复正常 `delta.content`
  - 修复：`patched_openai.py` 对 provider=zhipu 加 `extra_body={"thinking": {"type": "disabled"}}`（对话不需要思维链）
- **根因②（框架）**：langgraph 1.0.x `create_agent` 的 stream chunk 是**节点嵌套结构** `{'model': {'messages': [...]}}`，CLI 直接 `chunk.get("messages")` 取不到 → 空
  - 修复：CLI 加 `_iter_chunk_messages()` 递归取 messages（兼容嵌套/顶层两种形态）
- **教训**：① 推理模型的流式字段与 OpenAI 标准不同，patch 层要处理；② langgraph stream 输出结构以实测为准（打印 chunk 再写提取逻辑）

### P-017：create_agent 中间件参数是单数 `middleware`
- **现象**：M2 挂中间件时 `TypeError: create_agent() got an unexpected keyword argument 'middlewares'. Did you mean 'middleware'?`
- **根因**：langchain 1.2.x `create_agent` 的参数名是**单数 `middleware`**（接受 list），不是 `middlewares`
- **解法**：`create_agent(..., middleware=[TitleMiddleware(), ThreadDataMiddleware()])`
- **教训**：API 参数名以实际报错提示为准（"Did you mean"）；原版若传的是单数也说明这是官方命名

### P-018：SQLite 连接跨线程（LangGraph 工具后台线程跑 SQL）（M3）
- **现象**：CLI 问知识库时 `ProgrammingError: SQLite objects created in a thread can only be used in that same thread. The object was created in thread id 8358748544 and this is thread id 6175272960.`
- **根因**：`create_agent` 的工具调用在 **LangGraph 后台线程**执行；knowledge_tool 里 service/repo 持有主线程 init_db 创建的 conn，SQLite 连接默认 `check_same_thread=True` → 跨线程即报错
- **解法**：BaseRepository 支持 `db_path` 模式——`threading.local` 按线程建连接（复用 db.connect 统一配置 WAL/外键/Row）；CLI 中 memories/knowledge 改用 db_path，sessions 保持 conn 模式（只在主线程用）；补线程回归测试
- **教训**：**所有要进 LangGraph 工具链的数据访问都必须按线程建连接**——SQLite + 多线程的通用规矩；单测要覆盖"子线程执行 repo 查询"
- **关联**：M3-验证记录.md §5；test_knowledge_search.py::test_repo_thread_safe_with_db_path

### P-018b：疑问句被误沉淀为事实（M3 附带修复）
- **现象**：问"我叫什么"后，memories 表出现"用户叫什么"（错误事实）
- **根因**：extract_facts 只匹配句式，不判断语气——"我叫什么"也命中 `我叫(...)` 模式
- **解法**：捕获值含疑问词（什么/怎么/哪/为什么/吗/呢/如何）则跳过
- **教训**：事实提取必须先过滤疑问句，否则记忆里全是“用户叫什么”这类垃圾

### P-023：一次性调度时区不一致导致任务被跳过（M5）
- **现象**：一次性任务在默认调度线程中到达目标分钟时，没有进入执行队列。
- **根因**：`AutomationScheduler._tick()` 默认使用 aware 的 `datetime.now(UTC)`；`_parse_iso()` 却把保存时间的时区信息剥掉，返回 naive datetime。一次性任务比较 `now - scheduled_at` 会抛 `TypeError`，异常被单任务处理器捕获并记录 warning，任务因此跳过。
- **触发条件**：常见 CLI `--at "2026-10-03T09:00:00"` 存入 naive ISO 时间，同时使用默认后台 tick。现有测试注入 naive `now`，没有覆盖默认生产路径。
- **建议修复**：统一内部时间表示（全程 UTC aware，或统一转换为 naive UTC），并补一个使用默认时钟语义的一次性调度回归用例。
- **状态**：代码尚未修改；本轮仅登记审查发现。
- **关联**：`agentflow/scheduler/loop.py`、`doc/doc-dev/01-里程碑/M5-长任务与协作.md`

## M1 注释工程追加（2026-09-28，重写注释时回归抓出 3 个真 bug）

### P-008：BaseRepository 抽象方法名不一致
- **现象**：`Can't instantiate abstract class SessionRepository without implementation for 'insert'`
- **根因**：重写 repositories.py 时把抽象方法写成 `insert`，子类实际是 `create`
- **解法**：基类抽象方法统一为 `create / get / delete`（与子类一致）
- **教训**：改注释≠只改注释——跑回归才能发现"顺手改坏"的代码

### P-009：langgraph.prebuilt 没有 create_agent
- **现象**：`ImportError: cannot import name 'create_agent' from 'langgraph.prebuilt'`
- **根因**：prebuilt **1.0.8**（锁定版）只有 `create_react_agent`；`create_agent` 是 1.0.13+ 的新名字
- **解法**：与原版同款 API——`from langchain.agents import create_agent`（内部封装正确）
- **教训**：API 以**实际锁定版本的导出**为准，别信文档/记忆

### P-010：checkpointer from_conn_string 返回上下文管理器
- **现象**：`Invalid checkpointer provided. Expected BaseCheckpointSaver... Received _GeneratorContextManager`
- **根因**：langgraph-checkpoint-sqlite **3.x** 的 `SqliteSaver.from_conn_string()` 返回上下文管理器（需 with 才得实例）
- **解法**：直接构造 `sqlite3.connect(path, check_same_thread=False)` → `SqliteSaver(conn)`（原版注释也是这么写的：不用 from_conn_string 的 closing）
- **教训**：同 P-009——以实际版本的运行行为为准（回归测试的价值）

### P-011：datetime 工具非原版 → 改为 prompt 时间注入
- **现象**：用户要求"代码严格参考 EVOFLOW" → 核查发现原版 harness **没有** 独立时间工具
- **根因**：原版的时间能力 = `agents/lead_agent/prompt.py` 的 `format_runtime_now_for_prompt()`
  注入 system prompt（模型直接读到"2026-09-28 周一 (UTC+08:00)"，无需工具往返）
- **解法**：删除 `tools/builtins/datetime_tool.py`；新建 `agentflow/agents/lead_agent/prompt.py`
  （原版同款函数名/格式）；`make_lead_agent` 增加 system_prompt 参数（默认注入时间）
- **教训**：裁剪版也不能"自己发明结构"——先 grep 原版确认"这功能原版是怎么做的"再动手
- **附带修正**：thread_state 从 TypedDict 改为**继承 AgentState**（原版做法，reducer 官方维护）
