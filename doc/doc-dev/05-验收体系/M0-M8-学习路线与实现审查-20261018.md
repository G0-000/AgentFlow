建议保留 M0–M8 编号，把每个里程碑的状态拆成四类：

1. **理解**：能解释 EvoFlow 的设计和数据流。
2. **最小实现**：AgentFlow 有对应代码。
3. **集成**：从真实入口走通，而不只是模块单测。
4. **差异/后续**：明确省略了什么、为什么省略、何时再学。

不要把“组件测试通过”写成“端到端功能完成”。每个状态都应附对应测试或手工验收证据。

## 3. 优先修正的文档问题

### P1：M8 登录不能称为鉴权完成

`POST /api/auth/login` 会签发 JWT，但 `backend/app/gateway` 中没有校验 JWT 的中间件或依赖。模型、线程、run 等路由仍可不带 token 直接调用。前端把 token 放在普通请求头中，但 SSE 的直接 `fetch` 没带 token；目前之所以能工作，是因为服务端没有执行鉴权。

因此准确表述应为：**登录页和 token 签发已实现；受保护会话尚未实现**。这符合学习版边界，但不能把“登录/会话保持”解释成 API 已受保护。

### P1：M8 的真实模型回复不是 token/逐句流式

默认 runner 在 `backend/app/gateway/app.py` 里用 `agent.invoke()` 拿到整段回复，再 `yield` 一次。SSE 协议本身支持多条 `delta`，注入的假 runner 也可逐块输出；但默认真实模型路径通常是一条完整文本 `delta` 加 `done`。

应把“真模型 SSE 联调通过”与“真实逐 token 流式通过”分开。当前更准确的状态是：**SSE 传输链路通过，默认 runner 仍为缓冲式**。`doc-code/app/gateway/app.md` 已经解释这个差异，M8 与验收清单需要同步。

### P1：多会话不等于历史恢复

`chat-react.js` 切换会话时清空消息区，只显示提示，没有读取历史消息。会话 CRUD 和 thread id 隔离基本具备，但“切换/恢复历史”的验收并未完成。

建议验收名称改为“创建、列表、切换会话 id”；历史逐条恢复单独列为未完成项。

### P1：M8 的“全链路 = M1–M7 所有功能”不成立

现有证据主要覆盖 health、登录端点、模型/线程 API、run/SSE。它没有证明所有工具、记忆/知识、子代理、调度、MCP、trace、飞书渠道均能从界面操作；当前聊天 runner 还显式传入 `tools=[]`。

把验收项缩窄成“Web → Gateway → Agent 基础对话 + 模型配置”，其余能力按各自 API/IM/CLI 入口验收，不应宣称从 Web 覆盖 M1–M7 全功能。

- `M8-验收清单.md` 的 Archify 图注仍写“M8 尚未开始”，与当前实现冲突。
- M8 验收记录和学习手册仍写后端 **164 passed**；本次当前工作树实测为 **172 passed**。
- M7 文档的早期文件清单、测试数量和验收结果属于历史快照。2026-10-18 新增了 MessageBus/ChannelManager，但它们还未接入飞书实际收发链路；应继续标为“代码骨架存在，运行链未接线”。

这些内容应统一成一处当前状态来源，其余文件链接过去，避免多处各自维护状态数字。

## 4. 推荐的学习路线

| 顺序 | 学什么 | 读 EvoFlow 时的抓手 | AgentFlow 的练习与出口条件 |
|---|---|---|---|
| M0 | 仓库、环境、包边界、入口 | workspace、`langgraph.json`、核心与 app 分层 | 能启动/跑检查，并画出“请求从哪进、状态存哪”的图 |
| M1 | 最小对话闭环 | 配置 → 模型工厂 → ThreadState → Agent → checkpointer | CLI 单轮对话、跨进程恢复；说明业务会话与图 checkpoint 的区别 |
| M2 | 工具、中间件、流式 | 工具目录、工具结果、中间件装配、`agent.stream` | 一个工具 + 一个中间件；用测试证明工具调用和多块输出 |
| M3 | 记忆与知识检索 | 记忆写入/读取、知识 chunk/embedding/search | 把“对话记忆”和“文档知识库”分开，实现最小召回并指出线性检索边界 |
| M4 | 子代理与执行边界 | 委派/并发限制、沙箱路径校验、审计 | 证明并发上限、失败处理和越界拒绝；讲清路径隔离不等于 OS 级沙箱 |
| M5 | 长任务与恢复 | Plan/Goal 状态、checkpoint、协作生命周期、调度 | 拆成“可恢复长任务”与“时间触发调度”两个子目标，避免把二者混为一谈 |
| M6 | 扩展与治理 | MCP、授权、trace、社区 provider | 每个组件都区分“模块契约测试”和“接入 Agent/API 的集成测试” |
| M7 | 应用层与端口 | Gateway 装配、REST/SSE、Channel/MessageBus/Manager、R1 ports | 先跑 API，再把飞书接到统一总线；当前 AgentFlow 总线/管理器仍属未接线骨架 |
| M8 | Web 面板 | 页面生命周期、API client、SSE 消费、模型设置 | 按“登录签发 → API 保护 → 真流式 → 历史恢复 → 页面验收”顺序补齐，不以接口 curl 代替 UI 验收 |

每一步固定执行：**先画原版数据流 → 读关键 3–5 个文件 → 写自己的最小版本 → 跑针对性测试 → 记录与 EvoFlow 的差异**。大文件（如 EvoFlow 的 `lead_agent/agent.py`、前端 `ChatApp.tsx`）只从入口与数据结构分层阅读，不做从头到尾线性通读。
